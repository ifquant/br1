# 0155: 给 bookmarks workspace 补最小筛选和排序

## 这次改了什么

前一步我们给 `bookmarks workspace` 补了顶部工具层，但它还是只有“把所有书签直接平铺出来”这一种看法。

这会带来两个实际问题：

- 书签一多，想只看当前章节的内容不方便
- 用户有时想先看最近加的书签，有时又想按章节整理着看

所以这一步没有动持久化，只补展示层能力：

- 新增 `全部 / 当前章节` 筛选
- 新增 `最近添加 / 章节顺序` 排序
- 书签顶部状态 chips 会同步显示当前筛选和排序状态

这样 `bookmarks` 面板就不再只是一个静态列表，而开始像一个可操作的 workspace。

## 为什么这一步只改展示层，不改 controller

因为现在的需求只是：

- 改变“怎么看”书签
- 不是改变“怎么存”书签

所以最稳的做法是：

- 保持 `bookmarksController` 继续只负责状态恢复、增删和持久化
- 在 `ReaderSidebar` 本地派生 `filteredBookmarks` 和 `sortedBookmarks`

这样能避免把 UI 层的小需求过早塞进 controller，保持数据层边界清楚。

## 这次实现上的关键点

### 1. 筛选是基于 `chapterHref`，不是基于文案猜测

“当前章节” 不是拿章节标题字符串去猜，而是直接比较：

- `bookmark.chapterHref`
- `activeHref`

这样即使不同章节标题碰巧相同，也不会筛错。

### 2. “章节顺序” 现在是第一版整理视图，不是假装有真正 spine 顺序

这一步的“章节顺序”本质上是：

- 先按 `chapterLabel` 排
- 同章里再按 `createdAt` 倒序

它先解决“不要完全乱序”这个问题，但还没有接真正的书籍 spine/TOC 顺序。这个边界要明确，不要把第一版能力说得过头。

## 这次能学到的编程知识

### 知识点 1：筛选和排序通常应该基于同一份源数据串起来

这里的顺序是：

1. `bookmarksState.bookmarks`
2. 先得到 `filteredBookmarks`
3. 再得到 `sortedBookmarks`

这比“不同按钮各自改原数组”更稳，因为数据流是单向的，也更容易调试。

### 知识点 2：本地 UI 状态不一定要上升到 controller

不是所有状态都应该被抽到 controller。

像这次的：

- 当前选择了哪种筛选
- 当前选择了哪种排序

它们只影响 sidebar 这一块的展示，不影响全局业务规则，所以先保留在组件本地更合适。

## 还没做的事

- `bookmarks` 还没有真正按 TOC/spine 顺序排序
- 还没有“只看最近 N 条”或“按时间分组”
- 还没有给这套筛选/排序补专项自动化回归

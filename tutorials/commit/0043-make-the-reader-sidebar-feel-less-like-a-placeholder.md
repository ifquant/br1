# 0043: 先把 reader sidebar 从 TOC 壳压成更像侧栏系统

这次没有改 TOC 数据结构，也没有改章节跳转逻辑。  
目标只有一个：把左侧栏从“最小可用 TOC 壳”推进到更像真正阅读器侧栏。

## 这次做了什么

1. 重做了 sidebar 头部层级

在 [`ReaderSidebar.svelte`](/Users/dev/workspace2/hc_apps/br1/src/lib/components/reader/ReaderSidebar.svelte) 里，之前的头部很直接：

- `Reader`
- `目录`
- 一个 pin 按钮

这更像开发占位。

现在改成了更像侧栏系统的结构：

- 左边一个轻工具按钮
- 中间一组 labels
- 右边一个轻工具按钮

也就是说，视觉上更像“这是一个可操作的 panel”，而不是一块写着标题的区域。

2. 加了一层 book chip

`Readest` 的 sidebar 不是一打开就直接一列目录，它通常还有书籍上下文和更完整的 panel 结构。

所以这次补了一个很轻的 `book-chip`：

- 左边一条书脊
- 右边一组简短说明

它不是最终书卡，但已经能把侧栏从“裸 TOC 列表”往“有上下文的阅读 panel”推进一层。

3. 收紧了 tabs 和 TOC 的节奏

这次把这些地方都压了一轮：

- tabs 更薄
- tab 字更小
- TOC 顶部 spacing 更合理
- active 项有更明确但不夸张的高亮

这样 TOC 的感觉会更接近成熟阅读器，而不是一个普通列表。

4. 统一了按钮和背景权重

这次侧栏里所有轻按钮都走同一套 `ghost-button` 逻辑，hover 权重也统一了。

这种收口的好处是：

- panel 看起来像同一系统
- 而不是每个角落都有自己的一套按钮语言

## 你可以学到的具体知识

### 1. 为什么 placeholder 常常不是功能不够，而是“缺上下文层”

很多界面之所以显得像 placeholder，不是因为它没数据，而是因为它只有“核心列表”，没有“上下文层”。

例如这里的 sidebar：

- 只有 TOC
- 没有书籍上下文
- 没有 panel 的头部结构

就会很像“先放个列表看看”。

加一个轻量 `book-chip` 后，即使功能没变，用户也会更容易把它理解成真正的侧栏，而不是临时容器。

### 2. 为什么 active list item 的高亮不该只靠背景色

如果当前项只靠一层淡背景，很容易不够稳，尤其在阅读器这种低对比、安静配色里。

这次给 active TOC 项加了：

- 淡背景
- 左侧 inset 高亮线

这种组合比“只改背景色”更稳。  
因为它同时利用了：

- 面积变化
- 边缘锚点

用户会更容易在一长列条目里定位当前章节。

## 实际影响

现在左侧 sidebar 已经比之前更像一个真正的 reader panel 了：

- 头部不再像占位标题
- 有了更合理的 panel 上下文
- TOC 的节奏和 active 状态更稳

这还不是 `Readest` 那种完整 sidebar 系统，但它已经不再只是“最小 TOC 壳”。  
下一步如果继续，最合理的是收右侧 `bridge`，让三块 panel 的成熟度更接近。

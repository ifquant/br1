# 0173 按视图/排序/搜索上下文保留 library 滚动位置

## 这次改动做了什么

这一步继续执行 `02-03`，但只处理滚动行为。

主要变化有三件：

1. `library/+page.svelte` 现在会给 library 滚动容器建立一个显式的上下文 key
   - 桌面或 Web
   - 当前 `grid/list`
   - 当前排序方式
   - 当前是否处于搜索态
2. 每个上下文都会单独保存和恢复滚动位置
   - 切换排序后，不会总是回到一个混乱的历史位置
   - 搜索态和浏览态也不会共享同一份滚动值
3. `OverlayScrollbars` 的 auto-hide 从 `scroll` 调成了 `leave`
   - 更接近 Readest 的感觉
   - 同时把外层原生 `overflow` 收回，避免和自定义滚动条打架

## 为什么这一步重要

如果滚动位置没有和“当前视图上下文”绑定，library 很容易出现两类典型问题：

1. 你刚在列表模式下滚到很下面，切回网格模式后位置是错的
2. 搜索结果很短，但滚动条还继承了上一个浏览状态的位置

这种问题不会直接报错，但会让页面显得“不稳”，像是一个临时拼出来的界面。

这次改完后，library 至少具备了一个成熟阅读器该有的基础规则：

- 浏览态有浏览态的滚动记忆
- 搜索态有搜索态的滚动记忆
- 不同排序和视图不会共享一份脏的 scroll state

## 你可以学到的工程知识

### 1. 滚动位置本质上也是 UI state

很多项目把滚动当成浏览器自己的事，所以切视图、切 tab、切过滤条件时不会显式建模。

但只要页面是一个复杂工作台，滚动位置就不再只是“浏览器副作用”，而是一个真正的界面状态：

- 它和当前筛选条件有关
- 它和当前布局模式有关
- 它和用户刚才在看哪一段内容有关

所以更稳的做法是：

- 先定义滚动位置属于哪个上下文
- 再保存和恢复这个上下文对应的 scroll state

### 2. 第三方滚动容器最好只保留一个事实来源

这次把外层 `overflow: auto` 改回 `overflow: hidden`，原因很简单：

- 既然已经使用了 `OverlayScrollbars`
- 那滚动行为就应该由它接管

如果同时让原生 overflow 和 OverlayScrollbars 都参与，后面很容易出现：

- 双层滚动
- 视觉滚动条和真实滚动位置不一致
- 事件监听挂在错误容器上

这类问题在桌面壳里尤其明显。

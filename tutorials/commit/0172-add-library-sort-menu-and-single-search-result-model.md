# 0172 增加 library 排序菜单并收紧搜索结果模型

## 这次改动做了什么

这一步是 `02-03` 的第一刀，目标不是做复杂筛选，而是先把 library 的基础行为规则收紧。

主要变化有四件：

1. `LibraryHeader.svelte` 的“更多操作”不再是死按钮
   - 现在会打开一个最小可用的排序菜单
   - 支持：
     - 最近阅读
     - 最近导入
     - 书名
     - 作者
     - 格式
2. `library/+page.svelte` 新增了 `librarySortBy`
   - 书库显示顺序不再只靠一套硬编码规则
   - 改成了显式的展示层排序
3. 搜索行为被收成“单一结果集”
   - 一旦进入搜索态，就不再同时保留 `继续阅读 + 你的书库` 两个 section
   - 而是统一收口为一个 `搜索结果`
4. `最近导入` 不再拿 `lastOpenedAt` 冒充
   - 这次补回了 `importedAt`
   - 避免“名字叫最近导入，实际按最近阅读排”的假语义

## 为什么这一步重要

如果排序和筛选规则没有被明确写进状态模型，library 很容易呈现出“能用，但不稳定”的感觉：

- 今天是按最近阅读
- 明天可能又因为某个导入动作变成别的顺序
- 搜索时还保留多个 section
- 用户很难理解自己看到的结果到底代表什么

这类问题看起来不像 bug，但会持续消耗产品可信度。

这次改完后，至少有两条规则被正式固定下来：

1. 排序是一个显式可切换的 library state
2. 搜索态就是一个单一结果集，不再混合多个 section

## 你可以学到的工程知识

### 1. “展示排序”最好独立于“底层导入顺序”

底层数据常常有自己的自然顺序：

- 导入顺序
- 存储顺序
- 恢复顺序

但 UI 想表达的往往是另一件事：

- 最近阅读
- 最近导入
- 标题排序

所以最稳的方法通常不是反复重排源数据，而是在展示层做一个纯函数排序：

- 输入：原始 books + 当前 sort mode
- 输出：当前页面应该怎么显示

这样行为边界清楚，也更好测。

### 2. 搜索态通常应该压平信息架构

正常浏览时，多个 section 是有价值的：

- 继续阅读
- 主书库
- 最近导入

但搜索时，用户的目标已经变了：

- 不是“浏览结构”
- 而是“找到匹配项”

这时继续保留多个 section，往往只会制造噪音。

所以这次把搜索态压成单一结果集，是一个典型的“浏览态和搜索态分离”的产品决策。

# 0158: 给 reader header 补第一版阅读宽度菜单

## 这次改了什么

前面的 `⋯` 菜单还只是一个很薄的 quick-actions 集合，离 Readest 那种“真的承载阅读设置入口”的 header menu 还有明显差距。

这一步先补一个低风险、但很像阅读器设置菜单的入口：

- `阅读宽度`
  - `专注`
  - `标准`
  - `宽阔`

同时让正文舞台跟着这三个模式切换最大宽度，并把这个偏好记到本地。

这样 `⋯` 不再只是“还能点开什么动作”，而开始承担第一版 `View Menu` 的角色。

## 为什么先做阅读宽度，不先做字体/主题/分页设置

因为这一步的目标是：

- 先把菜单变成真正的阅读设置入口
- 但不要一下子碰 `ReaderViewport` 的排版引擎行为

阅读宽度正好满足这两个条件：

- 它是用户能立刻感知到的阅读设置
- 又只需要动 `ReaderStage` 容器宽度，不需要改底层阅读引擎

所以这是一个很稳的第一刀。

## 这次实现上的关键点

### 1. 菜单状态和舞台宽度通过一个简单的枚举联动

这里新增了：

- `ReaderViewWidthMode = 'focus' | 'standard' | 'wide'`

然后：

- `ReaderHeaderBar` 只负责显示当前模式和触发切换
- `ReaderStage` 负责真正把模式映射到容器宽度

这让菜单层和布局层的责任是分开的。

### 2. 这次只改 `canvas` 容器宽度，不碰 `ReaderViewport` 内部逻辑

真正影响正文宽度的是：

- `.canvas.window-mode`
- `.canvas.window-mode.focus-width`
- `.canvas.window-mode.wide-width`

也就是说：

- 引擎内部怎么渲染页内容，这一步没改
- 只是外面给它一个不同的可用版心

这很适合做第一版 view menu。

## 这次能学到的编程知识

### 知识点 1：先从“容器层设置”切入，往往比直接改引擎更稳

当你要给复杂系统加设置时，不要默认第一步就去动最底层。

像这次的阅读宽度，本质上可以先从：

- 外层容器宽度

入手，而不是一上来就改：

- 分页算法
- 字体计算
- 章节渲染逻辑

这能更快拿到用户可见收益，也更不容易把系统搞坏。

### 知识点 2：枚举型 UI 状态很适合配合 class 切换

这次的三档宽度是典型的枚举状态：

- `focus`
- `standard`
- `wide`

它非常适合映射成样式类，而不是在模板里堆很多 if/else。

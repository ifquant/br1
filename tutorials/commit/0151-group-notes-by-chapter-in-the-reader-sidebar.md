# 0151: 按章节分组显示 reader 里的笔记

## 这次改了什么

上一刀已经给 `notes` workspace 加了“全部 / 当前章节”筛选，但列表仍然是平铺的：

- 所有笔记一张张直接往下排

这对数量少时还行，但一旦跨多个章节积累起来，用户仍然很难快速建立上下文。

这一步不改数据模型，只把渲染方式升级成：

- 先按章节分组
- 每组显示章节标题和条数
- 组内再显示该章节下的笔记卡片

这样 notes workspace 的信息结构就更像阅读器里的“章节上下文 + 内容块”，而不是普通消息列表。

## 为什么先做分组，而不是继续加更多筛选

因为当列表可读性差时，继续堆筛选条件不一定是最优解。

当前更核心的问题其实是：

- 用户看到一条笔记时，不容易马上判断它属于哪个章节簇

按章节分组能直接解决这个上下文问题，而且比继续堆：

- 更多 filter chip
- 更多 toggle
- 更多菜单

更符合阅读器的工作流。

## 这次实现上的关键点

### 1. 先筛选，再分组

这次不是直接对 `notesState.notes` 分组，而是沿用上一步的思路：

1. 先得到 `filteredNotes`
2. 再在 `filteredNotes` 上派生 `groupedNotes`

这样结构更清楚：

- `notesState.notes`：原始数据
- `filteredNotes`：当前筛选视角
- `groupedNotes`：当前视角下的展示组织

这三层语义不要混在一起。

### 2. 分组键用 `chapterHref`，显示名用 `chapterLabel`

这次分组时没有直接拿 `chapterLabel` 做唯一键，而是：

- 用 `chapterHref` 做分组标识
- 用 `chapterLabel` 做展示标题

这样更稳，因为：

- `chapterLabel` 可能重复
- `chapterHref` 更接近真实资源定位

这是一个很典型的“稳定键 vs 展示文本”分离。

## 这次能学到的编程知识

### 知识点 1：列表的“筛选”和“分组”是两种不同维度

很多时候我们会把这两件事混在一起，但它们本质不同：

- 筛选：决定哪些数据出现
- 分组：决定出现的数据怎么组织

这次就是一个很标准的例子：

- `notesFilter` 决定看全部还是当前章节
- `groupedNotes` 决定这些结果怎样按章节组织

### 知识点 2：做派生视图时，优先保留原始数据不变

这里没有去改 `notesState.notes` 的结构，也没有把 grouped 数据写回 store。

而是保持：

- store 只存原始 notes
- 组件里按需派生 grouped 视图

这样做有两个好处：

- 数据层简单
- UI 改法更灵活

## 还没做的事

- notes 分组还不能折叠/展开
- 还没有章节内排序控制
- 还没有 notes 搜索
- 还没有 notes 分组视图的专项桌面自动化回归

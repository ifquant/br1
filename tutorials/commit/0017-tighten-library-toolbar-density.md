# 0017 Tighten library toolbar density

## 背景

`library` 现在已经先后处理过：

- 全局壳对页面主舞台的干扰
- shelf 里的解释型文案

接下来最显眼的差距就集中在顶部工具条。

和 `Readest` 对比时，`br1` 的问题不是“没有 header”，而是 header 还太像网页组件：

- 搜索条偏厚
- 按钮太松
- 工具按钮还是硬编码占位
- 整体更像一排控件，而不是一条系统级工具条

所以这一步的目标不是加功能，而是把 toolbar 的视觉密度压下来。

## 主要目标

- 收紧搜索条高度、字重和间距
- 让右侧工具按钮更薄、更接近阅读器 toolbar 的节奏
- 把按钮从硬编码占位改成数据驱动渲染，为后面继续对齐 `Readest` 留接口

## 改动概览

- 更新 `src/lib/components/library/LibraryHeader.svelte`
  - 把搜索条高度从更厚的网页输入框收紧成更薄的工具条搜索框
  - 调整搜索图标、placeholder 文本、边框透明度和内阴影
  - 用 `actions` 数组渲染右侧按钮，不再手写三颗独立占位按钮
  - 为不同按钮定义更接近真实图标节奏的字形尺寸

## 关键知识

### 1. 工具条视觉密度，通常靠一组统一尺寸规则，不靠单点“调顺眼”

像 `Readest` 这种桌面阅读器工具条，看起来很轻，但它的稳定感来自一组一起收紧的值：

- 搜索条高度
- 输入框内边距
- 图标字体大小
- 按钮点击区域
- 按钮之间的 gap

如果只改其中一个值，比如只把按钮缩小，但不一起改 gap 和输入框高度，最后会得到一种“元素都在缩，但节奏没收紧”的感觉。

所以这一步不是单独改某个按钮，而是一起压：

- `search-shell` 高度
- `actions` gap
- `button` 尺寸
- `search-copy` 字号

这类 UI 收口很像排版，不是单个值优化，而是比例系统优化。

### 2. Svelte 里把重复按钮改成数组驱动，比继续复制按钮标签更稳

这一步把三个工具按钮收成了一个 `actions` 数组，再用 `{#each}` 渲染。

这样做的直接好处有两个：

- 结构更统一，不会三个按钮越改越不一样
- 后面如果要把占位字形换成真实图标，只需要改数据和少量样式，不需要复制三份按钮模板

一个简单经验是：

- 当一组 UI 元素结构一样，只是文案、图标、样式类不同
- 就应该优先考虑数组驱动渲染

这不是为了“抽象而抽象”，而是为了减少未来微调时的重复劳动。

### 3. 占位图标阶段，也可以先把“光学重量”调对

我们现在还没上真实 icon，但并不等于这一层不能先做对。

即使只是：

- `+`
- `◫`
- `≣`

也可以先通过不同字号和轻微垂直偏移，把它们的视觉重量拉近。

这类处理的意义在于：

- 先把工具条节奏做对
- 后面再换真实 icon，风险更小

换句话说，很多视觉对齐可以先做“版式对齐”，不必等素材完全到位再开始。

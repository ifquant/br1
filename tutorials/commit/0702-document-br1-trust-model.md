# 0702 - 记录 br1 的安全信任模型

## 背景

Readest 的对应提交增加了威胁模型和事件响应流程，但 br1 不能直接复制其安全描述。br1 当前没有应用内账户系统，也没有启用 OPDS 网络代理；它真正需要说明的是本地书籍解析、Tauri 命令、应用数据、第三方翻译和同步端点之间的边界。

## 主要目标

- 让维护者知道哪些数据需要保护，哪些输入必须视为不可信。
- 区分已经存在的安全控制、依赖操作系统的假设和尚未修复的缺口。
- 为漏洞报告、分级、修复和披露提供一个最小但完整的流程。

## 改动概览

- 新增根目录 `SECURITY.md`，记录资产、可信组件、不可信输入和越界条件。
- 逐项说明书籍导入、渲染、Tauri IPC、持久化恢复、网络请求和依赖供应链的现有控制。
- 明确记录 CSP、iframe、明文本地数据、同步传输、资源限制和发布流程方面的已知缺口。
- 更新 Readest 对齐审计，将 `82deb85c6` 从待实现缺口改为已有 br1 安全文档覆盖，并把下一任务推进到 `S2-R03`。

## 关键知识

### 1. 威胁模型必须把“控制”和“假设”分开

路径 canonicalize、扩展名 allowlist 和 DOMPurify 是应用已经实现的控制；操作系统账户未被攻破、环境变量由本机操作者正确配置，则属于信任假设。把两者混在一起会让读者误以为应用可以抵御已经取得本机账户权限的攻击者。

### 2. 安全文档不能把未实现的能力写成保证

锁文件能让依赖变更可审计，但不能证明依赖没有漏洞；iframe 带有 `sandbox` 属性，也不能在 `allow-same-origin allow-scripts` 组合下被当作独立隔离保证。因此文档同时写出现有清洗边界和仍然缺少 CSP、防资源耗尽等事实。

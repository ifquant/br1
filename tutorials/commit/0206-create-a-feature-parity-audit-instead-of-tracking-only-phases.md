# 0206 建一份 Feature 总账，而不是只盯 phase 和局部页面

## 这次改动想解决什么

到这个阶段，`br1` 已经做了很多东西：

- library 导入和迁移
- EPUB / PDF 打开
- reader 布局
- 搜索
- 书签
- 笔记

问题不是“没做事”，而是**很容易只看到局部在进步**。

比如：

- reader 某条几何回归过了
- library 某个 section 更像了
- 某个 view menu 又补了一项

这些都是真的进展，但如果没有一份更高层的总账，就会出现两个风险：

1. 误以为“整体上已经很接近目标产品”
2. 继续在本地 reader 细节上优化，却忽略更大的功能缺口

你这次给的功能表，就是为了防止这种局部最优。

## 做了什么

### 1. 新增 `FEATURE-PARITY-AUDIT.md`

这次没有继续改产品代码，而是新增了一份：

- `.planning/FEATURE-PARITY-AUDIT.md`

它的作用不是记录某一刀怎么做，而是记录：

- `br1` 现在到底具备哪些产品能力
- 哪些只是“部分实现”
- 哪些还没开始
- 哪些是下一阶段最应该补的缺口

这是一份**产品总账**，不是实现日志。

### 2. 按 Feature 表而不是按页面做审计

这次故意没有按：

- library
- reader
- sidebar
- header

这种页面/组件方式写。

而是直接按你给的产品能力表来分：

- 多格式支持
- 阅读模式
- 全文搜索
- 批注 / 高亮
- 字体与布局
- 文件关联
- Library 管理
- 词典 / Wikipedia
- Parallel Read
- OPDS / Calibre
- DeepL / Yandex
- TTS
- 跨平台同步
- Koreader 同步
- Accessibility
- Visual & Focus Aids

这样以后就不会因为某个页面更像 `Readest` 了，就误判“这个 feature 已经完成”。

### 3. 每个 feature 都标了状态、证据、缺口、建议 phase

这份审计表不是一个空列表，而是每项都尽量补了四类信息：

- `Status`
- `Current Evidence`
- `Main Gap`
- `Suggested Phase`

比如：

- `Multi-Format Support` 不是简单写“有”
- 而是明确写成：
  - `EPUB / PDF` 强
  - `FB2 / MOBI / AZW3` 只是边界部分接线
  - `CBZ / TXT` 当前还不能算实现

这种写法的好处是：

- 不会把“accept 里有这个扩展名”误判成“产品能力已经完成”

### 4. 把 feature 重新分成 P0 / P1 / P2

这次顺手把能力分成三层：

- `P0 Core Reader`
- `P1 Advanced Reading Experience`
- `P2 Services and Ecosystem`

这个分层很重要，因为当前代码库明显是：

- `P0` 已经有明显进展
- `P1` 只有一部分骨架
- `P2` 基本没开始

如果不做这种分层，后面继续推进时很容易：

- 老是在 `P0` 里打磨局部
- 却忘了整张产品表上还有大量空白

### 5. 明确给出当前阶段的真实结论

审计表最后不是模糊表述，而是给了一个很明确的判断：

- `br1` 现在已经不是壳子
- 但它目前是 **core-reader strong, service/ecosystem weak**

这句话很关键，因为它把当前项目状态从“感觉上差不多了没有”变成了更硬的判断：

- 本地阅读器主干已经有力量
- 服务、同步、生态、扩展能力还远没有真正追平

## 这次顺手能学到的编程知识

### 1. phase 跟踪和 feature 跟踪解决的是不同问题

`ROADMAP` 和 phase 文档适合回答：

- 下一步工程怎么做
- 任务如何拆分

但它不一定适合回答：

- 产品到底已经具备哪些能力
- 哪些能力还只是局部实现

所以复杂产品通常同时需要两张表：

- 一张是实现计划表
- 一张是 feature 能力表

少了后者，就很容易在局部优化里迷路。

### 2. “有相关代码”不等于“feature 已完成”

这是这次审计最重要的一条经验。

比如：

- import accept 里写了 `.fb2`
- 不等于 `FB2` 阅读已经完成

因为真正的 feature 完成，至少要看：

- 是否能打开
- 是否能稳定读
- 是否有恢复语义
- 是否有相关自动化或产品链路证据

这比“源码里搜到关键字”要严格得多。

## 还没有处理什么

- 这一步没有修改 roadmap 结构
- 没有开始新的功能实现
- 也没有把这份审计表自动回填到 phase 状态里

这一步只是先把产品总账立起来，让后续规划不再只围绕局部页面推进。

# 0184: 让 Readest 兼容字段从“抽象说明”变成“可审计信息”

## 这次改动解决什么

虽然 `br1` 现在已经会把 Readest 条目标成：

- `Readest 兼容`
- `保留 封面 / 简介 / 元数据 / 阅读位置`

但这个说明还是偏粗。

问题在于：

- “元数据”到底是语言、出版者，还是别的东西？
- “阅读位置”到底只是有进度百分比，还是连恢复定位都保留了？

如果这些信息只停留在抽象标签上，用户很难真的判断当前兼容面到底到了哪里。

## 这次具体做了什么

### 1. 把兼容说明从粗粒度词汇拆成具体字段

文件：`src/routes/library/+page.svelte`

`mapLibraryRecord()` 里生成 `compatibilityLabel` 的逻辑现在更细了。

之前是：

- 封面
- 简介
- 元数据
- 阅读位置

现在改成了更可审计的字段：

- 封面
- 简介
- 语言
- 出版者
- 恢复定位
- 如果没有恢复定位但有进度，则显示阅读进度

这样一眼就能知道当前是：

- 只保留了百分比进度
- 还是连真正的恢复定位也保留下来了

### 2. 把 `progressLocation` 正式带进 library 共享类型

文件：`src/lib/library/types.ts`

新增了：

- `progressLocation?: string`

并让 `ContinueReadingBook` 也显式携带这个字段。

这一步的意义是：  
以后只要 library 里的任意组件需要展示“恢复定位”，就不必再重新回到 route 层拼接临时字段。

### 3. 在详情面板里直接显示真实的恢复定位

文件：`src/lib/components/library/ContinueReadingShelf.svelte`

现在 continue reading / recent reading 的详情面板里新增了一行：

- `恢复定位`

它会直接显示：

- `book.progressLocation`

如果没有，则显示：

- `未记录`

这样 Readest 兼容条目的“阅读状态保留”终于不只是一个抽象描述，而是能在详情里看到实际被保留下来的定位值。

## 这次学到的编程知识

### 知识点 1：审计型 UI 要避免“过于抽象的成功文案”

像：

- 元数据
- 阅读位置

这种词对开发者来说很方便，但对用户和排障来说信息量不够。

更稳的做法是尽量把抽象能力拆成具体字段，比如：

- 语言
- 出版者
- 恢复定位
- 阅读进度

这样用户和开发者都更容易判断：

- 到底兼容了什么
- 缺了什么
- 当前实现离目标还有多远

### 知识点 2：共享类型里多放一个“状态字段”，常常比在组件里临时拼接更好

如果某个字段已经被证明是产品上真实有价值的信息，比如：

- `progressLocation`

那更好的做法通常是：

- 把它提升进共享类型

而不是在某个组件里临时从别的字符串推断。

这样数据流更直，也更利于后面继续扩 library / reader 对齐。

## 这次没有处理什么

- 没有新增 Readest 迁移桌面回归
- 没有继续扩 Readest 读取字段范围，只是把已经读取到的字段展示得更明确
- 没有改 reader 对恢复定位的消费方式，只处理了 library 的兼容可见性

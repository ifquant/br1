# 0041: 先把 reader 的 chrome 从“开发控件”压成“阅读器控件”

这次改动没有碰 `foliate-view` 的逻辑，也没有继续扩 reader 功能，而是先处理一个更基础的问题：

`reader` 的顶部和底部太像开发页面了。

之前的状态更像这样：

- 顶部有 `Reading` 这种环境标签
- 右上角有 `Open / Aa / 🔊 / ☰`
- 底部有 `Prev / Start / Next`
- 再加一堆直接暴露给用户的原始状态文本

这些信息虽然对开发阶段有帮助，但放在阅读器里会很重。`Readest` 的 reader chrome 更薄、更克制，正文才是主角。

所以这一刀的目标很窄：

- 不改引擎
- 不改数据流
- 只把 reader 的 header/footer 压得更像阅读器 chrome

## 这次做了什么

1. 去掉顶部的环境标签感

在 [`ReaderWorkspace.svelte`](/Users/dev/workspace2/hc_apps/br1/src/lib/components/reader/ReaderWorkspace.svelte) 里，去掉了 `Reading` 这种 eyebrow。

取而代之的是：

- 第一行：书名
- 第二行：作者 + 当前章节

这样顶部信息就更像真正的书籍信息条，而不是一个工作台标题。

2. 把顶部按钮从“功能词”压成“工具位”

原来顶部按钮里最重的是 `Open` 这个词。现在改成更像工具条的一组轻按钮：

- `⌂`
- `Aa`
- `🔊`
- `⋯`

同时补了：

- `aria-label`
- `title`

也就是说，视觉上更轻，但语义没有丢。

3. 把底部导航从“操作面板”压成“阅读条”

原来的底部是：

- `Prev`
- `Start`
- `Next`
- 多段原始状态字符串

现在改成更像阅读器的方式：

- `‹ · ›` 这种轻量导航位
- 中间保留进度滑杆
- 右边只留下 `位置 / 格式 / 字体` 这种压缩 metadata

这样底栏更像阅读器 chrome，而不是一排调试按钮。

4. 收紧 footer 的视觉权重

这次顺手把底栏样式也压了一层：

- 更薄的 top border
- 更轻的背景
- 更小的字
- 统一大写小标签感
- metadata 改成小圆点分隔

这类小调整单独看不起眼，但它们会显著影响“像不像成品阅读器”。

## 你可以学到的具体知识

### 1. 为什么图标化按钮要补 `aria-label` 和 `title`

当按钮文字被压成图标时，视觉是更干净了，但语义会变差。

例如：

- `⌂`
- `⋯`

如果不补说明：

- 屏幕阅读器读不出用途
- 鼠标悬停时也没有提示

所以常见做法是：

- 视觉上用轻图标
- 语义上补 `aria-label`
- 交互上补 `title`

这能同时兼顾：

- 美观
- 可访问性
- 可发现性

### 2. 为什么先压 chrome，而不是先继续扩阅读功能

因为阅读器的主角是正文，chrome 是服务层。

如果正文已经能打开，但 chrome 还像调试台，那么用户对产品成熟度的判断会被严重拖累。  
这属于很典型的 **信息层级问题**：

- 用户第一眼不该先看到“你能做哪些操作”
- 而该先感受到“这里适合读书”

所以这一步虽然不增加新功能，但它会直接提高 reader 的产品感。

## 实际影响

现在 `reader` 顶部和底部已经比之前更像阅读器 chrome 了：

- 书名/作者/章节关系更清楚
- 控件更轻
- 底部更像阅读条
- 正文区域的主角地位更明显

这还没到 `Readest` 的成熟程度，但它先把最重的开发味压下去了，后面再做 reader 舞台和 sidebar 对齐时会顺很多。

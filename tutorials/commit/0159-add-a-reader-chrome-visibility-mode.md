# 0159: 给 reader view menu 补界面显隐模式

## 这次改了什么

上一刀我们已经让 `⋯` 菜单开始承担第一版 `View Menu` 的角色，但它还只管“阅读宽度”，离真正的阅读设置还是太薄。

这一步继续补一个低风险、但很像成熟阅读器的设置项：

- `界面显隐`
  - `自动`
  - `总是显示`

对应效果是：

- `自动`：保持现在这套 window mode 下的顶部/底部控制层自动显隐行为
- `总是显示`：让 header/footer 常驻，不再自动隐藏

同时把这个偏好记到本地，下次打开还能恢复。

## 为什么先做“界面显隐”，而不是直接做字体/分页设置

因为这一步的目标仍然是：

- 让 `⋯` 更像真正的阅读设置菜单
- 但不要直接碰 `ReaderViewport` 的排版与渲染行为

界面显隐正好满足：

- 用户能直接感知
- 只影响 chrome 层
- 不需要改正文引擎

所以它很适合接在“阅读宽度”后面做第二刀。

## 这次实现上的关键点

### 1. `chromeMode` 只控制控制层，不控制正文

这次新增了：

- `ReaderChromeMode = 'auto' | 'always'`

它只决定：

- header 是否自动隐藏
- footer 是否自动隐藏

不会影响：

- 正文宽度
- 分页方式
- 文本渲染

这样边界很清楚。

### 2. 自动隐藏定时器会尊重 `always`

这一步最关键的不是菜单按钮本身，而是让原来的自动隐藏逻辑接受新模式：

- `scheduleChromeHide()` 在 `always` 模式下直接返回
- `always` 模式会主动把 `chromeVisible` 维持为 `true`

这样“总是显示”才不是视觉假开关，而是真的控制行为。

## 这次能学到的编程知识

### 知识点 1：设置项的第一步，通常是先把“已有隐式行为”变成“显式模式”

原来 header/footer 的自动显隐已经存在，只是它是隐式规则。  
这一步做的事，本质上是把它变成一个显式用户设置：

- `auto`
- `always`

很多设置功能的第一刀，都可以这样做。

### 知识点 2：行为设置要同时改“触发条件”和“状态兜底”

如果只改定时器，不改 `chromeVisible` 的兜底逻辑，界面还是可能因为别的路径被隐藏。  
所以这里同时做了两件事：

- 改 `scheduleChromeHide()` 的触发条件
- 改 reactive 兜底，让 `always` 保持可见

这比只改一个点更稳。

## 还没做的事

- `view menu` 还没有字体、主题、分页等真正深入的阅读设置
- 还没有专项自动化回归直接覆盖 `自动 / 总是显示` 切换
- `chrome` 的显隐策略仍然是当前 br1 版本，不是完整的 Readest 交互复刻

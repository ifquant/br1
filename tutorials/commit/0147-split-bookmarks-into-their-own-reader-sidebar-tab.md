# 0147: 把书签从 notes 面板里拆成独立 sidebar tab

## 这次改了什么

到上一步为止，`bookmarks` 虽然已经能：

- 保存
- 展示
- 跳转
- 删除

但它们还混在 `notes` tab 里。这样的问题很直接：

- 书签和笔记是两种不同对象
- 却挤在同一个工作区里
- 用户要找书签时，还得先跨过一段笔记 UI

这一步只做一个信息架构切片：

- `SidebarTab` 新增 `bookmarks`
- sidebar 新增 `书签` tab
- 把书签列表从 `notes` 面板独立出去
- 书签相关动作默认留在 `bookmarks` tab，不再回跳到 `notes`

这让 `reader` 的 sidebar 更接近 Readest 的“不同工作对象，占不同工作面”的结构。

## 为什么这一步不先改 header

因为现在的 header 还没有完全按 Readest 的面板组织来做。

如果这一步同时去改：

- header 按钮布局
- sidebar tab 结构
- 快捷键

就会把一个原本清晰的信息架构调整，变成多层 UI 一起改的大切片。

所以这里先只做：

- sidebar 内部结构拆分

等它稳定后，再决定 header 是否要加独立的 bookmarks 切换入口。

## 这次实现上的关键点

### 1. `SidebarTab` 扩容后，相关事件类型要一起跟上

这类改动最容易漏的不是组件本身，而是所有把 tab 当联合类型传来传去的地方。

这次一起调整了：

- `SidebarTab` 类型
- `ReaderStage` 里 `switchsidebartab` 的事件类型
- sidebar 自己的 tab 列表和 panel 分支

这种“联合类型扩容”最好一次性搜全，否则很容易出现某些地方还是旧字符串集合。

### 2. 书签动作默认保持在书签 workspace

现在：

- 顶栏星标新增/取消书签后，会切到 `bookmarks`
- 点击书签跳转后，也保持 `bookmarks`
- 删除书签后，仍留在 `bookmarks`

这是一个很细但重要的交互点：  
用户当前在操作哪个对象，界面就尽量留在哪个对象的 workspace 里。

否则很容易出现“我明明在管理书签，界面却跳回笔记面板”的割裂感。

## 这次能学到的编程知识

### 知识点 1：信息架构调整，不一定等于大重构

很多人一听到“拆分 workspace”，就会下意识觉得要做大手术。

但实际上，如果：

- 数据已经存在
- 动作已经存在
- 只是容器划分不对

那完全可以先做这种小范围重排。

这类改动对用户感知往往很强，但代码风险不一定高。

### 知识点 2：对象分组的边界，通常应该跟用户心智对齐

笔记和书签都是“阅读附属物”，但用户心智并不把它们当成一回事：

- 书签：是位置
- 笔记：是内容

当这两类对象被强行塞进一个 workspace 时，界面会显得“什么都有，但不清楚”。

把它们分开，常常比继续往一个面板里堆更多功能更有价值。

## 还没做的事

- header 还没有独立的 bookmarks 切换按钮
- 书签 tab 还没有更像 Readest 的摘要/筛选/更多操作
- notes 和 bookmarks 还没有进一步做成更完整的独立 workspace 体系
- 还没有针对 bookmarks tab 的专项桌面自动化回归

# 0115 给笔记编辑和删除补宿主 store 桌面回归

这次没有继续加新的 notes 功能，而是把已经存在的“编辑笔记”和“删除笔记”锁进桌面自动化里，确认它们不只是改了 sidebar 文案，而是真的写进了宿主 store。

## 为什么要补这条回归

前面已经有两条与 notes 相关的桌面回归：

- legacy notes 迁移到宿主 store
- 正文高亮反向聚焦 sidebar note

但这两条都还没覆盖最容易悄悄退化的一层：  
**编辑和删除是不是只改了当前窗口状态，而没有真正持久化。**

如果这里断掉，最常见的用户体感就是：

- 当下看起来改成功了
- 一重开书，旧 note 又回来了
- 或者删了 sidebar 卡片，但正文高亮和 store 里还残着

所以这次把“编辑 -> 重开仍在”和“删除 -> 重开仍没了”变成了正式桌面回归。

## 这次具体做了什么

1. 继续复用 [e2e/app.e2e.ts](/Users/dev/workspace2/hc_apps/br1/e2e/app.e2e.ts) 里的 `reopenReaderWithLegacyNote()`
   这条 helper 已经被前两条 notes 桌面回归验证过，能稳定准备出：
   - 打开书
   - 预埋 legacy note
   - 重开后迁移进宿主 store
   - 在 sidebar notes 面板里确认 note 已可见

2. 新增桌面回归：
   - 覆盖 `window.prompt`，把编辑结果固定成 `edited note body`
   - 点击 `编辑`
   - 断言当前窗口里 note 文案已更新
   - 关闭并重开同一本书
   - 再断言编辑后的内容仍然存在
   - 点击 `删除`
   - 断言当前窗口里 note 消失
   - 再关闭并重开
   - 断言 note 仍然不存在

## 这次对应的知识点

### 1. UI 自动化里，“重开后仍然成立”比“当下看起来变了”更有价值

很多状态类 bug 只看当前窗口是看不出来的。  
因为当前窗口可能只是前端内存状态变了，而真正的宿主 store 还没更新。

所以像 note 编辑/删除这种功能，最有价值的断言不是：

- “按钮点了”
- “当前 DOM 变了”

而是：

- “重开后依然是对的”

这才能验证真正的持久化链。

### 2. 让多条回归复用同一个准备 helper，可以显著降低桌面测试抖动

桌面自动化最容易坏的不是最终断言，而是：

- 选哪本书
- 什么时候关窗
- 什么时候重开
- 什么时候 notes 面板真的 ready

把这些准备动作抽成一个共享 helper，能让后续新增回归更像“补覆盖率”，而不是“每次重新和桌面生命周期搏斗一遍”。

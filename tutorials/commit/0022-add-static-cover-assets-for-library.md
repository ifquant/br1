# 0022 Add static cover assets for library

## 背景

前一轮已经把 `library` 的 toolbar 做得更像真实产品了，但书架 still 有一个明显短板：

- 书卡大多数视觉仍然靠 fallback cover 撑着

这会带来两个问题：

- 页面始终有“样例页”的味道
- 继续细调 fallback cover，回报会越来越低

因为真实阅读器书架的视觉重心，本来就不应该落在假封面上，而应该落在真实封面容器和真实内容资产上。

所以这一步不去接真实后端元数据，而是先补一层本地静态封面资产。

## 主要目标

- 让 `library` 的样例书先拥有真实封面资源
- 把书卡主视觉从 fallback cover 切到真实封面容器
- 保持这一步仍然是视觉资产升级，不引入数据逻辑

## 改动概览

- 新增 `static/covers/*.svg`
  - 为当前样例书生成了几张本地静态封面资源
- 更新 `src/routes/library/+page.svelte`
  - 给样例书数据加上 `coverUrl`
- 更新 `src/lib/components/library/BookshelfPreview.svelte`
  - 当书存在 `coverUrl` 时优先渲染真实封面图片
  - 没有 `coverUrl` 时仍然回退到 fallback cover

## 关键知识

### 1. 当真实数据还没接上时，用“稳定的本地视觉资产”过渡，比反复雕 fallback 更划算

视觉开发常见一个阶段：

- 逻辑和数据还没接好
- 但页面已经需要开始长成产品

这时候有两种常见做法：

- 一直优化 fallback cover
- 先接一层本地静态资源

第二种通常更划算，因为它更接近真实产品结构：

- 书卡最终本来就应该优先显示真实封面
- fallback 只是兜底

如果你一直打磨 fallback，本质上是在优化一个未来应该退居二线的东西。

这一步先把样例书接上本地封面，就是为了让视觉重心早点回到正确位置。

### 2. 视觉占位也可以分层：数据占位、资源占位、逻辑占位

很多人会把“还没接真实功能”理解成“只能全部先假着”。

其实可以拆成三层：

- 数据占位：书名、作者还是样例数据
- 资源占位：封面已经用本地静态资源替代纯文字假封面
- 逻辑占位：点击、搜索、导入行为还没接

这样分层推进有个好处：

- 页面会越来越像真实产品
- 但你不需要一次把所有事情都做完

这是一种非常适合 UI 迭代的方式。

### 3. 用本地 `static/` 资源做 Svelte 封面占位时，路径应尽量稳定、简单

这一步把封面放进了：

- `static/covers/...`

然后在页面数据里直接写：

- `'/covers/political-order.svg'`

对 SvelteKit 来说，这是最省事也最稳定的静态资源路径方式之一。

好处是：

- 不需要额外 import bundler 资源
- 不容易因为组件位置变化导致相对路径混乱
- 后面替换成真实远程 URL 或 metadata 字段也更顺

一个简单经验是：

- 如果资源是页面级静态视觉资产
- 优先考虑放到 `static/`

这样组件里读取会更直接。

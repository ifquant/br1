# 0060：空书库时自动从 Readest 吸纳已有书库

这次修的不是“功能不存在”，而是“功能放在那里但用户实际走不到”。上一版虽然已经加了从 `Readest` 导入的能力，但它还是依赖一个显式入口。只要入口没看到、没点到，`br1` 看起来就还是“没有书”。

所以这次把策略改成：

- 如果 `br1` 自己的书库是空的
- 且本机检测到 `Readest` 书库
- 那么 `library` 首次加载时直接自动迁移一次

这样用户打开 `br1`，就更像打开一个已经积蓄过内容的阅读器，而不是一个还要先手动配置的空壳。

## 改了什么

- 在 `/Users/dev/workspace2/hc_apps/br1/src/routes/library/+page.svelte`
  - `loadLibrary()` 现在会先读 `br1` 自己的书库
  - 如果书库为空但检测到 `Readest`，会自动调用迁移逻辑
  - 自动迁移后重新加载 `br1` 的持久化书库，再渲染到页面上
- 手动入口仍然保留：
  - 如果后续你还想继续从 `Readest` 追加导入，按钮还在

## 这次值得学的两个知识点

### 1. 能力已经存在，不等于用户能走到

这是前端很常见的一个误区。

你可能已经做了：

- `detectReadestLibrary()`
- `importReadestLibrary()`
- 一个迁移按钮

但如果用户第一次打开页面时看到的还是空壳，他的结论只会是：

- “没有书”

而不是：

- “哦，这里其实有个隐藏入口能导进来”

所以当某个能力是**初始化体验的关键**时，常常应该改成：

- 自动触发
- 或者非常强的默认引导

而不是只做一个“存在但不打扰”的按钮。

### 2. 初始化逻辑里，先判断“空态”再做自动修复，是一种很稳的产品工程手法

这次逻辑的关键条件是：

- `records.length === 0`
- `readestSummary.available`

这类判断很常见，因为它能把自动行为限制在最合理的场景：

- 只在用户还没有自己数据的时候帮他填第一桶内容
- 一旦用户已经有自己的数据，就不再强行替他做导入

这比“每次都自动同步”更安全，也更容易控制副作用。

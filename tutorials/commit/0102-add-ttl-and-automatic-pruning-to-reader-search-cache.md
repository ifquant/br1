# 这次提交讲了什么

这次把 `reader search cache` 从“能存下来”推进到“后台能自己收拾”：

- 缓存带 TTL
- 读缓存时会自动处理过期项
- 写缓存时会自动做单本书和全局的回收
- 旧格式缓存会被就地升级，不需要人工清理

## 你能学到的具体知识

### 1. 持久化缓存不能只存结果，还要存生命周期元数据

如果磁盘缓存只写一组结果数组，它永远不知道自己：

- 什么时候写入
- 什么时候该过期
- 最近有没有被访问

所以这次把缓存文件从“裸结果数组”升级成了带元数据的 entry：

- `savedAt`
- `lastAccessedAt`
- `expiresAt`
- `schemaVersion`
- `results`

这样宿主层才能实现真正的缓存治理，而不是把目录越堆越大。

### 2. 最稳的迁移方式通常是“读时兼容 + 写时升级”

这次没有直接要求用户手动删旧缓存。  
做法是：

1. 先尝试按新格式读
2. 如果失败，再按旧格式读
3. 旧格式能读出来时，立刻回写成新格式

这叫“读时兼容，写时升级”。  
它很适合缓存、索引、配置文件这类可以渐进迁移的数据。

## 这次结构为什么放在 Rust 宿主里

缓存 TTL 和自动回收属于“后台维护策略”，不应该散在前端组件里。  
所以这次逻辑都放在 [lib.rs](/Users/dev/workspace2/hc_apps/br1/src-tauri/src/lib.rs)：

- `load_reader_search_cache`
- `save_reader_search_cache`
- `prune_reader_search_cache_root`
- `prune_reader_search_cache_book`

这样前端继续只关心：

- 读缓存
- 写缓存
- 清缓存

而真正的磁盘治理由宿主统一负责。  
这比把 TTL 判断塞进 Svelte 组件里更稳定，也更接近一个正式桌面应用的做法。

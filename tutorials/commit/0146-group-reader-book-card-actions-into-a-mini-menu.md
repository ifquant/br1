# 0146: 把 reader 顶部书籍卡片的动作收成一个小菜单

## 这次改了什么

上一刀已经给 sidebar 顶部书籍卡片补了两个动作：

- `回到书库`
- `打开原文件`

但它们还是两颗并排裸按钮，信息层和动作层还比较散，不太像 Readest 那种更收束的 card 结构。

这一步只做一个很小的整理：

- 保留一个直接主动作 `回到书库`
- 把更多动作收进一个 `⋯` 小菜单
- 菜单先承载：
  - `回到书库`
  - `打开原文件`

这样顶部卡片开始更像一个有主动作 + 次动作的真实入口，而不是一排不断外长的按钮。

## 为什么还保留一个直接主动作

如果把所有动作都塞进菜单，结构会更整齐，但效率会下降。

`回到书库` 是当前最常用、也最符合这个 card 语义的动作，所以保留为直接按钮更合理。

而像 `打开原文件` 这种相对次级、且只在特定来源可用的动作，更适合进入菜单。

这其实是在做一个常见的 UI 分层：

- 主动作：直接露出
- 次动作：收进菜单

## 这次实现上的关键点

### 1. 菜单是组件内的局部状态，不需要提升到 route

这次新增的 `bookMenuOpen` 只是一个纯 UI 状态：

- 开了没
- 点外面要不要关
- 按 `Escape` 要不要关

它不影响业务数据，也不需要跨组件共享。

所以它最适合就地放在 `ReaderSidebar.svelte`，而不是往 route/store 里提升。

### 2. 菜单里的动作仍然复用原有 callback

虽然动作呈现方式从“直接按钮”变成了“菜单项”，但业务调用没有变化：

- 还是 `callbacks.onGoToLibrary`
- 还是 `callbacks.onOpenSourcePath`

这说明这一步是 **UI 组织重排**，不是业务重构。

当一轮改动只是组织方式变化时，尽量不要顺手改数据流，这样风险最低。

## 这次能学到的编程知识

### 知识点 1：局部 UI 状态不要无意义上提

很多人会下意识把菜单开关也塞进全局 store 或 route 里。

但像这种：

- 只影响当前组件
- 页面刷新不用记住
- 不参与业务逻辑

的状态，放在组件本地最干净。

### 知识点 2：做 UI 收束时，优先重排动作层，不先改业务层

这次我们把按钮收进菜单，用户看到的界面组织已经明显更接近成熟产品，但底层调用完全没变。

这类改动价值很高，因为：

- 用户感知明显
- 回归面很小
- 不会把原来的能力链路一起改坏

## 还没做的事

- 菜单还没有书籍详情 / 更多设置
- 还没有 keyboard shortcut / focus trap 之类更完整的 menu 行为
- `asset` 打开路径仍然没有“打开原文件”能力
- 还没有这个 mini menu 的专项桌面自动化回归

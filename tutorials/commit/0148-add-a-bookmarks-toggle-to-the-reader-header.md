# 0148: 给 reader header 补一个独立的书签面板入口

## 这次改了什么

上一刀已经把 `bookmarks` 从 `notes` 里拆成了独立的 sidebar workspace，但顶部控制层还没跟上：

- 现在 header 有搜索入口
- 有笔记入口
- 但没有书签入口

这会导致一个不协调的状态：

- sidebar 里已经有独立书签工作区
- header 却还像书签不存在一样

这一步只补一个很小的对齐：

- 在 `ReaderHeaderBar` 里新增独立的 `书签` 面板按钮
- 让它和现有的 `搜索 / 笔记` 一样走 `onOpenSidebarTab(tab)`
- 保持原来的星标继续只负责“给当前位置加/取消书签”

这样 header 和 sidebar 的信息架构终于对齐了。

## 为什么要保留“星标”和“书签面板按钮”两个入口

因为它们解决的是两件不同的事：

- `星标`：当前这一页要不要加入书签
- `书签面板按钮`：我要不要打开书签工作区

如果把这两个动作混在一个按钮里，用户就会遇到典型冲突：

- 点一下到底是“收藏当前位置”
- 还是“打开书签列表”

把“当前状态切换”和“进入工作区”分开，是更清晰的设计。

## 这次实现上的关键点

### 1. 新入口完全复用现有 sidebar tab 机制

这次没有新增任何新的 route 逻辑，也没有发明新的事件：

- 还是 `onOpenSidebarTab(tab)`
- 还是 `SidebarTab`
- 还是现有的 `toggleTab/openTab` 语义

这说明这一步不是业务扩张，而是把已经存在的信息架构补到顶部控制层。

### 2. 按钮的 active 态跟现有 search/notes 保持一致

新按钮的激活条件依旧是：

- `activeSidebarTab === 'bookmarks'`
- 且 `sidebarVisible`

这样整个 header 的面板按钮组保持统一规则，不会出现某个按钮用一套激活逻辑、另一个按钮又是另一套。

## 这次能学到的编程知识

### 知识点 1：工作区入口和对象动作，最好分开建模

这是很多复杂界面会遇到的问题。

例如这里：

- `★ / ☆` 是对象动作
- `🔖` 是工作区入口

如果只看“都和书签有关”，很容易误以为它们应该是同一个按钮。

但从用户任务看，它们本质完全不同，所以应该拆开。

### 知识点 2：当底层结构已存在，先补入口层，往往比继续加功能更值

bookmarks workspace 已经存在时，继续堆更多 bookmarks 功能，不一定比先把入口补全更有价值。

因为入口层缺失会直接影响 discoverability：

- 功能有了
- 用户却不容易发现

这类问题通常应该优先解决。

## 还没做的事

- header 的书签按钮还只是最小入口，没有做 Readest 那种更完整的图标体系和 hover 策略
- 还没有针对 header 书签按钮的专项桌面自动化回归
- 还没有把 bookmarks workspace 做到更完整的摘要、筛选或更多操作

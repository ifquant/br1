# 0161: 把 reader view menu 拆成设置区和操作区

## 这次改了什么

前几刀我们已经往 `⋯` 菜单里塞进了几类内容：

- 阅读氛围
- 界面显隐
- 阅读宽度
- 导入书籍
- 固定/取消固定侧栏

功能上已经比之前强很多，但结构上还不够清楚，因为：

- 前三项是“阅读设置”
- 后两项是“命令型动作”

如果继续平铺在一起，菜单会越来越像杂物堆。

所以这一步不加新能力，只整理信息架构：

- 上半区明确为 `阅读设置`
- 下半区明确为 `操作`
- 中间加分隔线
- `Open book` 改成更产品化的 `导入书籍`
- `Pin sidebar` 改成 `固定侧栏 / 取消固定侧栏`

## 为什么这一步值得单独做

因为一个菜单不只是“能点很多东西”就够了，更重要的是：

- 用户能不能快速理解这里面哪些是设置
- 哪些是立即执行的动作

这类整理不会直接增加功能数量，但会显著提升菜单的可理解性。  
Readest 那种成熟感，很多时候就来自这种结构清晰，而不是单纯按钮更多。

## 这次实现上的关键点

### 1. 用 `menu-section` 和 `menu-subsection` 明确层级

这一步把菜单分成了两层：

- 一级：`阅读设置` / `操作`
- 二级：`阅读氛围` / `界面显隐` / `阅读宽度`

这样前面几刀加出来的设置项终于有了一个清楚的归属。

### 2. 文案从“开发者动作名”收回到产品语言

像：

- `Open book`
- `Pin sidebar`

这种更像内部动作名。  
现在改成：

- `导入书籍`
- `固定侧栏 / 取消固定侧栏`

会更像真实产品里的菜单。

## 这次能学到的编程知识

### 知识点 1：信息架构优化本身就是实现工作，不只是文案修修补补

很多人会低估这种调整，觉得它只是“改改标题”。  
实际上它在做的是：

- 重新定义内容分组
- 让不同类型的动作进入不同层级
- 让以后继续扩展菜单时有结构可依

这属于真正的界面实现工作。

### 知识点 2：菜单会逐步演化，先分区再扩展比一直平铺更稳

如果一个菜单注定还会继续长，最稳的做法通常是：

1. 先建立分区
2. 再往各区里继续补功能

这样后续新增项不会持续打乱已有结构。

## 还没做的事

- `view menu` 还没有更深入的字体、分页、主题设置
- 还没有专项自动化回归直接覆盖菜单分区和动作文案
- 目前菜单的图标和视觉密度还没有完全对齐 Readest

# 0069 优先把 EPUB 放到书库前面，方便先验证 reader 主链

这次提交的目标不是“假装修好 PDF”，而是先让 `library -> reader` 的主验证路径更稳定。

当前 `br1` 的第一本真实书经常来自 Readest 迁移书库，而这些书里 PDF 很多。PDF 这条支路还在继续修，所以如果第一本书总是 PDF，你每次点第一本书都会先撞到同一个已知问题，反而看不清 EPUB 主链是不是已经通了。

所以这一步做得很小：

- 对桌面持久化书库做一个仅用于展示层的排序
- `EPUB` 优先
- 其次是 `FB2 / MOBI / AZW3`
- `PDF` 往后放
- 同格式内再按导入时间倒序

这样做的实际效果是：

- 你点 `library` 第一本文书时，更大概率先进入可验证的 EPUB 路径
- 我们可以先把“阅读器主链”验证通，再单独修 PDF 支路

## 改动点

- 在 [library/+page.svelte](/Users/dev/workspace2/hc_apps/br1/src/routes/library/+page.svelte) 增加 `readerValidationRank()`
- 在加载本地书库、迁移 Readest 书库、以及本机导入新书时，都统一走 `sortRecordsForReaderValidation()`
- 这一步不改后端持久化格式，只改前端展示顺序

## 这次顺手能学到的知识

### 1. “验证友好排序” 是很实用的调试手法

当系统有多条输入路径，但其中一条已知有 bug 时，不一定非要先把所有问题一起啃完。

你可以先让 UI 优先暴露“更容易成功的输入样本”，这样：

- 更容易验证主链是否已通
- 更容易把问题切成更小的支路
- 不会被已知 bug 一直挡住视线

这不是掩盖 bug，而是把验证顺序排对。

### 2. 排序最好放在“展示层边界”，不要太早污染底层数据

这次没有去改 Rust 侧的库记录顺序，也没有修改存盘 JSON，而是只在 Svelte 页面把 `PersistedLibraryBook[]` 排序后再映射成 UI。

这么做的好处是：

- 数据层仍然保持原始语义
- 验证策略只影响当前界面
- 以后如果要改成“最近阅读优先”或“用户自定义排序”，不需要先回滚底层存储规则

# 0171 对齐 library 的封面尺度和卡片结构骨架

## 这次改动做了什么

这一步继续执行 `02-02`，但目标更窄：

- 对齐封面尺寸
- 对齐行高节奏
- 对齐悬浮动作
- 让导入 tile 在 `grid/list` 两种视图里使用同一套卡片骨架

具体来说：

1. `BookshelfPreview.svelte` 新增了统一的尺寸变量
   - `--cover-radius`
   - `--list-cover-width`
   - `--card-row-height`
2. `list` 视图里的真实书籍卡片和导入 tile 现在走同一套 `cover + meta + trailing actions` 结构
3. `grid/list` 的 hover 动作都被收进统一的显隐规则
   - 默认隐藏
   - hover / focus 时出现
4. 封面 hover 时的边框和阴影会一起提升
   - 不再只是纯文字区域在变

## 为什么这一步重要

上一刀已经把“字段层级”收紧了，但卡片骨架仍然不够一致：

- grid 和 list 像两套不同组件
- 导入 tile 还是特殊布局
- 右侧动作区和封面区的节奏不稳定

这种问题很常见：

一个页面视觉上看起来差不多，但只要条目一多，就会暴露出组件结构不统一：

- 某些卡片显得高
- 某些卡片显得挤
- hover 反馈不在同一个层
- 导入入口像“插进来的一块广告”

这次做完后，`BookshelfPreview` 更像一套完整的书架条目系统，而不是“普通书卡 + 特殊导入卡 + 特殊列表卡”的拼装。

## 你可以学到的工程知识

### 1. UI 一致性很多时候来自“骨架变量”，不是来自单个样式值

如果只靠零散改：

- 这里 `76px`
- 那里 `84px`
- 某处 `122px`
- 某处 `8px`

最后一定会漂。

更稳的方法是先把“这一类组件的固定骨架”抽出来，例如：

- cover 宽度
- cover 圆角
- list 行高

这样后面继续调视觉时，调的是“系统参数”，不是继续堆 magic number。

### 2. 视觉一致性往往比功能一致性更早暴露出组件边界问题

导入 tile 这次没有增加任何新逻辑，但只要它结构和普通书卡不一致，整个书架就会显得不专业。

这说明一个实用原则：

- 如果两个东西在产品上属于同一类条目
- 那它们应该先共享结构，再谈局部差异

否则用户不会觉得“这是一个系统”，只会觉得“这是几个组件摆在一起”。

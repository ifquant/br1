# 01-03 Plan: 为导入基线补足基本验证和失败处理

**Phase:** 1 - Library Ingestion Baseline  
**Plan:** 01-03  
**Status:** Planned  
**Requirements:** LIB-01, DSK-02  
**Depends on:** 01-01, 01-02  
**Parallel-safe:** No  

## Why This Plan Exists

`Phase 1` 处理的是输入层基线。如果没有验证护栏和清晰失败语义，前两份计划即使实现了，也很容易在后续 library 视觉对齐或 reader pipeline 调整时被重新打坏。`01-03` 的重点不是“多写测试”，而是明确导入链路最关键的契约：什么算成功、什么算失败、出现失败时用户或开发者能看到什么，以及这些事实如何被自动化或最小验证记录下来。

## Brownfield Context

当前项目已有不错的桌面自动化基线，但仍然偏向 reader 结果验证：

- `e2e/app.e2e.ts`
  - 更强于 reader window / restore / geometry 回归
- `tests/e2e/library-smoke.spec.ts`
  - 更像 web 壳层 smoke
- `scripts/automation/test-tauri-webdriver.sh`
  - 已经是标准桌面验证 harness

导入基线当前的不足：

1. 导入成功后的产品契约没有独立成一条测试心智模型
2. 导入失败、路径不可访问、非桌面场景等失败语义还比较分散
3. 有些路径仍以 `console.error` 为主，缺少统一可观察结果
4. 没有把“输入层通过”与“reader 内部渲染通过”严格区分开

## Scope

本计划只补 Phase 1 所需的最小验证和失败处理，不做大规模测试扩写。

In scope:

- 明确导入、迁移、打开原文件、打开 reader 的最小成功/失败语义
- 为输入层补至少一条 focused verification path
- 确保失败时有一致的错误出口，便于手工验证和自动化断言
- 在文档或测试描述中明确“输入层”和“reader 渲染层”的边界

Out of scope:

- 建立完整单元测试体系
- 覆盖所有格式和所有桌面菜单动作
- 处理 Phase 4 之后的 reader 渲染验证细节

## Deliverables

1. 导入基线的最小验证矩阵
2. 输入层失败语义的明确出口
3. 一条或多条 focused regression / manual verification 记录
4. 后续执行 Phase 1 时可直接复用的验证 checklist

## Execution Plan

### Wave 1: 定义导入基线契约

1. 列出 Phase 1 需要锁住的主场景
   - 系统选书导入成功
   - Readest 藏书迁移成功
   - 点击书籍打开独立 reader 窗口
   - 打开原文件成功
2. 列出最小失败场景
   - 非桌面环境误用
   - 文件路径无效
   - 打开窗口失败
   - 迁移失败或无数据
3. 明确这些场景应该返回什么
   - UI 提示
   - 可断言错误
   - 允许的 fallback

### Wave 2: 收敛验证方式

1. 能复用现有 desktop regression 的优先复用
2. 只在确有价值时新增 focused 用例
3. 如果某些失败路径不适合自动化，明确列成手工验证项

### Wave 3: 形成 Phase 1 护栏

1. 把验证命令写成稳定 checklist
2. 保证后续执行 01-01 / 01-02 时都知道该跑什么
3. 为后续 Phase 2+ 保留“输入层已验证”的事实基础

## Task Breakdown

### Task 1: 定义主路径和失败路径

把以下行为从“代码实现细节”提升为“产品契约”：

- 导入返回的记录可用于书库和 reader
- reader 打开失败时不应该静默
- 非桌面场景下要报明确错误
- `openLibraryBookPath()` 失败时能被上层观察到

### Task 2: 收紧验证矩阵

优先使用：

- `pnpm check`
- `git diff --check`
- targeted desktop regression

补充原则：

- 锁最脆弱的输入层路径
- 不为了“测试很多”而写低价值用例

### Task 3: 写清失败语义

如果实现中仍然需要保留 `console.error`，至少要同时满足：

- 上层有明确返回值或抛错
- UI 或测试层可判断是否失败
- 失败不会伪装成成功

## Verification Checklist

- `pnpm check`
- `git diff --check`
- 若涉及 Rust 命令或 host 行为变更：`cargo check --manifest-path src-tauri/Cargo.toml`
- targeted desktop regression or explicit manual desktop flow check

## Risks

- 如果把验证目标定得过宽，会把 Phase 1 变成测试工程而不是导入基线工程
- 如果不区分输入层和渲染层，回归结果会很难解释
- 如果失败语义仍然散落，后续 phase 会继续把 bug 当布局问题处理

## Done When

1. Phase 1 的输入层主路径和最小失败路径都被定义清楚
2. 至少一条 focused verification path 能证明导入基线仍然成立
3. 后续执行 01-01/01-02 时，开发者知道要如何判断“这一步真的没破”

## Not Planned Here

- 不建立全面 controller 单元测试
- 不覆盖所有 reader 功能路径
- 不处理 Phase 4 之后的格式渲染细节

# 01-01 Plan: 统一本地图书导入、读取和路径访问服务

**Phase:** 1 - Library Ingestion Baseline  
**Plan:** 01-01  
**Status:** Planned  
**Requirements:** LIB-01, DSK-02  
**Depends on:** None  
**Parallel-safe:** No  

## Why This Plan Exists

`br1` 现在已经有本地图书导入、`Readest` 迁移、`library-file` reader 打开、打开原文件等链路，但这些能力分散在 `library` route、service 封装和 Tauri command 之间，仍然带有“为了先跑通而补丁式拼接”的特征。`Phase 1` 的第一刀不是继续做视觉，而是先把导入和路径服务统一成一条稳定输入层，避免后续书库对齐、reader 对齐和自动化回归都建立在脆弱的文件访问行为上。

## Brownfield Context

当前已有可复用实现：

- `src/lib/services/libraryPersistence.ts`
  - `loadPersistedLibraryBooks()`
  - `importLibraryBooks()`
  - `importReadestLibrary()`
  - `openLibraryBookPath()`
  - `toReaderAssetHref()`
  - `toReaderStartHref()`
- `src/routes/library/+page.svelte`
  - 已串起桌面选择文件、导入、迁移、打开 reader
- `src/routes/reader/+page.svelte`
  - 已支持 `source=library-file` 的打开路径
- `src-tauri/src/commands/library.rs`
  - 已有导入和迁移 command

当前主要问题：

1. 导入、迁移、路径访问和“打开原文件”是可用的，但还没有一个被明确命名的“ingestion boundary”
2. `library` route 仍承担了过多导入流编排逻辑
3. 失败处理和桌面/非桌面分支已经存在，但约束不够集中
4. 现有自动化更偏 reader 结果验证，导入基线本身的产品契约还不够明确

## Scope

本计划只处理导入与路径访问服务层，不做后续视觉对齐。

In scope:

- 统一 library import / Readest migration / 打开原文件 / reader href 构建这组基础能力的服务边界
- 减少 route 层对底层桌面行为的直接拼接
- 补齐导入与路径失败的明确契约
- 让后续 `01-02` 能直接复用更稳定的打开链路

Out of scope:

- library 页面的视觉改版
- continue reading 分区
- reader 主舞台或布局问题
- 搜索、笔记、书签或格式扩展

## Deliverables

1. 一个更清晰的 library ingestion service 边界
2. route 层对导入、迁移、路径访问的调用面收敛
3. 桌面和非桌面场景下更明确的错误/降级语义
4. 至少一条能覆盖导入输入层的验证路径

## Execution Plan

### Wave 1: 梳理输入层契约

1. 审计 `libraryPersistence.ts` 与 `library/+page.svelte` 的职责分布
2. 定义统一的导入动作集合
   - 本地文件导入
   - Readest 本地库迁移
   - 打开原文件
   - reader href 构建
3. 明确哪些逻辑应留在 route
   - 纯 UI 状态
   - 用户触发顺序
   - 打开后是否自动跳转
4. 明确哪些逻辑必须下沉到 service
   - 桌面环境判断
   - 路径选择/打开
   - 导入失败语义

### Wave 2: 收敛实现

1. 在 service 层补统一 helper 或 action-oriented API
2. 精简 `library/+page.svelte` 里的导入分支，减少重复桌面判断
3. 保持现有 `reader` 打开 href 兼容，不破坏后续 Phase 4 的 reader 打开链路
4. 避免把视觉或排序逻辑混进这次重构

### Wave 3: 验证和护栏

1. 跑 `pnpm check`
2. 视改动范围选择：
   - `cargo check --manifest-path src-tauri/Cargo.toml`
   - 或最小桌面手工导入验证
3. 如果适合自动化，补一条 focused regression
   - 优先锁“从系统导入一本书后可以形成稳定的 library record”

## Task Breakdown

### Task 1: 审计现有导入与路径服务

检查以下问题并记录到实现注释或 plan 执行笔记中：

- 哪些 API 已经是产品层契约
- 哪些只是 route 为了绕开限制的局部拼接
- 哪些错误目前只是 `console.error`
- 非桌面 fallback 是否仍在做不必要的模拟

### Task 2: 统一服务边界

目标不是简单“多加几个 helper”，而是让 library 输入层更像一个明确模块。优先考虑：

- 命名清晰的 import action 封装
- 显式返回导入结果或失败原因
- 对 `openPath`、file picker、Readest migration 统一桌面约束

### Task 3: 简化 library route

`src/routes/library/+page.svelte` 应该保留：

- UI 状态
- section 数据组织
- 用户触发后的页面更新和跳转

应尽量拿掉：

- 深层桌面环境判断
- 分散的失败分支
- 和 service 重复的路径拼接规则

### Task 4: 验证

最少需要：

- 类型检查通过
- 无格式错误
- 一条真实导入路径被验证

## Verification Checklist

- `pnpm check`
- `git diff --check`
- 如涉及 Rust command 改动：`cargo check --manifest-path src-tauri/Cargo.toml`
- 如涉及桌面交互变化：最小手工导入流或 targeted desktop regression

## Risks

- 如果把 route 层逻辑过度抽走，可能让后续 library 视觉阶段更难改
- 如果这一步顺手修改 reader 打开协议，可能会误伤 Phase 4
- 如果把 desktop-only 限制藏得太深，web fallback 会变得更难理解

## Done When

1. 导入、迁移、路径访问的主服务边界更清楚
2. `library/+page.svelte` 的导入流拼接明显减少
3. 后续 `01-02` 可以直接建立在这个输入层之上
4. 验证记录真实存在，而不是只写计划

## Not Planned Here

- 不在本计划中追求 `Readest` 书库视觉完全对齐
- 不在本计划中处理 continue reading 产品化
- 不在本计划中处理 reader 内部布局或多格式扩展

# 01-02 Plan: 固化 library-file 与独立 reader 窗口的桌面打开链路

**Phase:** 1 - Library Ingestion Baseline  
**Plan:** 01-02  
**Status:** Planned  
**Requirements:** LIB-01, DSK-02  
**Depends on:** 01-01  
**Parallel-safe:** No  

## Why This Plan Exists

在 `br1` 里，“一本书从 library 被点开后，进入独立 reader 窗口继续阅读”已经是核心产品路径。但当前这条链路仍然跨越了 `library` route、reader route、`readerWindow` service、`libraryPersistence` href 构建和 `ReaderViewport` 的 source resolution。它现在能工作，但还没有被当成一个正式的桌面协议面来收敛。`01-02` 的目标就是把 `library-file -> reader window` 这条主路径固化，保证后面 Phase 4/5/6 对 reader 的所有对齐工作都建立在稳定的打开协议之上。

## Brownfield Context

当前已有可复用实现：

- `src/routes/library/+page.svelte`
  - 已能在导入后自动打开第一本书
  - 已能点击卡片打开 reader
- `src/lib/services/readerWindow.ts`
  - 已能在桌面端创建/复用独立 reader 窗口
- `src/lib/services/libraryPersistence.ts`
  - 已能构建 `toReaderAssetHref()` / `toReaderStartHref()`
- `src/routes/reader/+page.svelte`
  - 已能解析 `source=library-file`
- `src/lib/components/reader/ReaderViewport.svelte`
  - 已能接收 `library-file` control request

当前主要问题：

1. `library` 侧的“自动打开第一本书”“重开当前书”“打开原文件”和 reader window 协议仍然耦得较紧
2. reader 窗口创建/聚焦与 href 构建之间还缺少显式产品契约
3. 一旦 Phase 4 改 reader open pipeline，这条路最容易被误伤
4. 当前桌面自动化更关注最终渲染结果，不一定明确锁住“打开协议本身”

## Scope

本计划只处理 library-file 打开链路和 reader window 协议收敛，不处理 reader 内部渲染细节。

In scope:

- 收紧 `library -> href -> readerWindow -> reader route -> controlRequest` 这条协议链
- 明确首次打开与重新开始阅读的两类 href 语义
- 减少 library route 对 reader window 行为的偶发拼接
- 为后续窗口流转和恢复位置对齐提供稳定基座

Out of scope:

- reader 主舞台排版问题
- EPUB/PDF 正文渲染问题
- 位置恢复精度升级
- library 视觉对齐和 continue reading 产品化

## Deliverables

1. 明确的 library-file reader open 协议边界
2. `openReaderTarget()` 与 href 构建职责更清晰
3. library route 里“打开书”相关路径更少重复分支
4. 一条能锁住主桌面打开链路的验证手段

## Execution Plan

### Wave 1: 梳理打开协议

1. 审计两类打开入口
   - 导入后自动打开
   - 已在书库中的书籍点击打开
2. 对比两类 href
   - `toReaderAssetHref()`
   - `toReaderStartHref()`
3. 明确哪些状态应该在 href 中表达
   - source
   - path
   - label
   - fraction / location
4. 明确哪些状态不应由 library route 临时拼接

### Wave 2: 收敛 library-file 桌面流

1. 统一打开当前书的 service 调用面
2. 保持独立 reader 窗口作为主桌面打开模式
3. 确保“重开当前位置”和“从头开始”语义不混淆
4. 保证失败时能回到明确错误，而不是静默失败

### Wave 3: 验证

1. 跑 `pnpm check`
2. 如果改动触及 Rust 或窗口创建契约，补 `cargo check`
3. 优先补或复用 targeted desktop regression
   - 打开第一本 library 书籍进入独立 reader 窗口
   - library-file EPUB/PDF 恢复路径仍然可用

## Task Breakdown

### Task 1: 审计 href 与 open flow

检查：

- `toReaderAssetHref()` 与 `toReaderStartHref()` 是否已经覆盖产品语义
- `openReaderTarget()` 是否承担了不属于窗口层的逻辑
- `library/+page.svelte` 是否还保留额外拼接逻辑

### Task 2: 固化桌面打开路径

优先方向：

- 把“打开书”变成明确 service contract
- 让 route 只负责决定何时打开，不决定如何构造整个打开协议
- 保持 reader route 的 query 解析与 controlRequest 兼容

### Task 3: 加护栏

至少需要一条针对主打开链路的事实验证。理想情况下直接使用或增强：

- `opens the first library book in a separate reader window`
- `restores a library-file epub into a visible reading position inside the reader stage`
- `reopens a library-file pdf with restored progress inside the reader stage`

## Verification Checklist

- `pnpm check`
- `git diff --check`
- 如改动窗口/host 协议：`cargo check --manifest-path src-tauri/Cargo.toml`
- targeted desktop regression for library-file open path

## Risks

- 如果擅自改 query 协议，容易和现有 reader route/automation 脱节
- 如果把窗口逻辑过度埋进 service，后续排查桌面问题会更难
- 如果把“打开原文件”和“打开 reader”混成同一个动作，会模糊产品语义

## Done When

1. library-file 主打开链路有清晰协议和调用边界
2. 独立 reader 窗口仍然是稳定主路径
3. 当前自动化可以覆盖至少一条事实上的 library-file 打开回归
4. 后续 Phase 4/6 可以直接建立在这条稳定打开链路上

## Not Planned Here

- 不处理 reader 内部内容白屏或版式问题
- 不处理恢复精度细化
- 不处理 continue reading 书库分区

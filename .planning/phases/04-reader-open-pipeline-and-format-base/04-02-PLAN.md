# 04-02 Plan: 稳定 PDF 打开链路与 vendor/wasm 方案

**Phase:** 4 - Reader Open Pipeline and Format Base  
**Plan:** 04-02  
**Status:** Planned  
**Requirements:** FMT-02, FMT-05  
**Depends on:** 04-01  
**Parallel-safe:** No  

## Why This Plan Exists

`PDF` 是当前 `br1` 和 `Readest` 差距最大的格式基座之一。虽然已经有 `setup-vendors`、`pdf.js` 和桌面回归，但这条线仍容易受 vendor 输出、wasm 文件、运行时 MIME/路径处理影响。必须把它收成正式方案，后面 reader 对齐才不会频繁返工。

## Brownfield Context

当前已有实现：

- `setup-vendors` 已生成 `pdf.js` 相关静态资源
- 已有 focused desktop regression 覆盖 `PDF` 重开与恢复进度
- `jbig2.wasm` 已走正式资源输出路径

当前问题：

1. `PDF` 依赖面仍然比 `EPUB` 更脆弱，容易被 vendor 产物或路径变化打断
2. 某些错误会表现为 MIME/资源加载失败，而不是明确的 `PDF` 打开错误
3. `setup-vendors`、运行时依赖和 UI 错误面之间还没有完全闭环

## Scope

In scope:

- 审计并收口 `pdf.js` / wasm / vendor 静态资源接入方式
- 明确 `PDF` 打开失败时的错误出口
- 补足 `PDF` 的 focused regression 和必要的构建校验

Out of scope:

- `EPUB`
- reader 视觉和交互层
- 非 `pdf.js` 的替代渲染方案

## Canonical References

- `scripts/setup-vendors.*`
- `public/` 下的 `pdf.js` 相关资源
- `src/lib/components/reader/ReaderViewport.svelte`
- `e2e/app.e2e.ts`
- `AGENTS.md` 中关于 `setup-vendors` 的规则

## Deliverables

1. 明确、正式的 `PDF vendor / wasm` 接入方式
2. `PDF` 打开失败时更可诊断的错误表现
3. `PDF` focused regression 和构建检查

## Execution Plan

### Wave 1: 审计 vendor / wasm 依赖面

1. 梳理当前 `setup-vendors` 输出和运行时消费路径
2. 核对 `pdf.js` / wasm / worker 等静态资源是否完全由正式流程生成
3. 找出仍依赖临时路径或隐式 MIME 假设的部分

### Wave 2: 收口 PDF 主路径

1. 统一 `PDF` 资源查找和 reader 打开逻辑
2. 收口运行时错误面，明确失败提示
3. 保证 `setup-vendors` 缺失时的失败语义可理解

### Wave 3: 验证与护栏

1. 跑 `PDF` focused desktop regression
2. 跑 `setup-vendors` / build 相关检查
3. 记录剩余 `PDF` 特殊边界

## Verification Checklist

- `pnpm check`
- `pnpm exec wdio run wdio.conf.ts --mochaOpts.grep '<PDF focused tests>'`
- `pnpm run setup-vendors` 或等价 vendor 校验
- `git diff --check`

## Done When

1. `PDF` 打开链路依赖正式 vendor 方案
2. wasm / vendor 缺失时不会表现成难以理解的白屏
3. 自动化能覆盖至少一条真实 `PDF` 打开或恢复路径

## Not Planned Here

- 不处理 `EPUB`
- 不处理 reader 视觉和菜单层
- 不引入新的 PDF 渲染内核

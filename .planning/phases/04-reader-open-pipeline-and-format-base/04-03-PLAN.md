# 04-03 Plan: 收口格式基座、错误处理与跨格式打开服务

**Phase:** 4 - Reader Open Pipeline and Format Base  
**Plan:** 04-03  
**Status:** Planned  
**Requirements:** RDR-01, FMT-01, FMT-02, FMT-05  
**Depends on:** 04-02  
**Parallel-safe:** No  

## Why This Plan Exists

`EPUB` 和 `PDF` 各自稳定之后，还需要把 reader 打开服务层和错误面统一起来。否则后面继续做 reader shell、layout 和行为对齐时，打开路径仍会散落在 route、service、viewport 之间，维护成本会持续偏高。

## Brownfield Context

当前已有实现：

- `library-file` / `asset` reader target 已经结构化
- `EPUB` / `PDF` 都已有 focused regression
- reader route 已经承担主要 orchestration

当前问题：

1. 跨格式打开服务仍可能有分散入口
2. 错误提示和 stage error 语义还不完全统一
3. 某些格式差异被塞在组件内，不利于后续扩展和调试

## Scope

In scope:

- 收口跨格式打开服务和共享错误语义
- 减少 route / viewport / format helper 之间的职责重叠
- 为后续 reader layout parity 提供更稳的格式基座

Out of scope:

- 视觉对齐
- 搜索、笔记、书签的更深行为
- 新格式支持

## Deliverables

1. 更一致的跨格式打开服务边界
2. 统一的 reader 错误与降级语义
3. 为 Phase 5 准备好的 reader 打开基座

## Execution Plan

### Wave 1: 审计跨格式服务边界

1. 梳理 `asset` / `library-file` / `window` / `web fallback` 之间的职责
2. 标出仍在 route 或 viewport 里硬编码的格式差异
3. 识别错误提示和 stage error 的重复实现

### Wave 2: 收口打开与错误面

1. 统一跨格式打开服务的输入与输出
2. 收口共享错误提示和失败降级
3. 减少 reader route 中与格式细节强耦合的逻辑

### Wave 3: 回归与交接

1. 重跑 `EPUB` / `PDF` focused regression
2. 验证桌面独立窗口和 library 打开流未回退
3. 记录交给 Phase 5 的已知边界

## Done When

1. reader 打开服务不再按格式散落
2. 错误和降级语义在跨格式上更一致
3. Phase 5 可以专注几何与视觉，而不是继续返工格式基座

## Not Planned Here

- 不处理视觉和布局细节
- 不处理服务型能力
- 不新增新的书籍格式

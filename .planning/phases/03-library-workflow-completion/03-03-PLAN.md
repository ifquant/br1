# 03-03 Plan: 完成 Readest 藏书数据兼容与迁移

**Phase:** 3 - Library Workflow Completion  
**Plan:** 03-03  
**Status:** Planned  
**Requirements:** LIB-05  
**Depends on:** 03-02  
**Parallel-safe:** No  

## Why This Plan Exists

`br1` 第一阶段的目标不是自造一套新书库，而是对齐 `Readest`。这意味着本机已有 `Readest` 藏书数据不能只是“导入一下文件”，而应该尽可能兼容其现有元数据、阅读状态和本地组织方式。

## Brownfield Context

当前已有实现：

- `detectReadestLibrary()`
  - 已能发现本机 Readest 书库
- `importBooksFromReadest()`
  - 已能迁入一批本地记录
- `library/+page.svelte`
  - 已有 Readest 迁移 banner

当前问题：

1. 当前迁移更像“把文件导进来”，还不是完整的 Readest 藏书兼容
2. 某些 metadata、状态字段和组织信息未必完整保留
3. 用户难以判断哪些内容是兼容、哪些只是重新导入

## Scope

In scope:

- 审计当前 Readest 迁移读取了哪些字段
- 补足缺失的本地 metadata / 阅读状态兼容
- 明确迁移 banner、提示文案和降级语义

Out of scope:

- 在线同步账号能力
- 远端服务数据兼容
- 非 Readest 来源的第三方书库迁移

## Deliverables

1. 更完整的 Readest 本地藏书兼容说明和实现
2. 迁移后 metadata / 状态在 library 中更完整可见
3. 迁移流程的成功、空结果、失败语义更明确

## Execution Plan

### Wave 1: 审计 Readest 数据兼容面

1. 梳理当前读了哪些 Readest 本地字段
2. 找出 library 仍未消费或未映射的部分
3. 区分“兼容原数据”和“重新导入生成新数据”的边界

### Wave 2: 补迁移字段与提示

1. 补足最关键的 metadata / 状态字段兼容
2. 收口迁移 banner 和提示文案
3. 明确重复导入、空书库、部分缺失的处理

### Wave 3: 验证迁移闭环

1. 验证发现 Readest 书库
2. 验证迁移后的条目在 library 中可见且状态合理
3. 如需要，补 focused desktop/manual 验证记录

## Verification Checklist

- `pnpm check`
- `cargo check --manifest-path src-tauri/Cargo.toml`
- `git diff --check`
- 手工桌面迁移复审

## Done When

1. Readest 本地书库在 `br1` 中不再只是“能导进文件”
2. 迁移后的 metadata / 状态具备清晰兼容语义
3. 用户能理解当前是兼容、迁移，还是重新导入

## Not Planned Here

- 不处理在线账号和远端同步
- 不处理 reader 工作区
- 不处理服务型能力

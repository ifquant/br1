# 03-02 Plan: 打通阅读状态回流与书库排序

**Phase:** 3 - Library Workflow Completion  
**Plan:** 03-02  
**Status:** Planned  
**Requirements:** LIB-04  
**Depends on:** 03-01  
**Parallel-safe:** No  

## Why This Plan Exists

书库能不能真正像 `Readest` 一样工作，关键不在“显示了哪些卡片”，而在 reader 里的阅读状态是否能稳定回流到 library。当前 `br1` 已经有一部分最近阅读、进度和状态字段，但这条链路还没有被当成正式产品工作流来收口。

## Brownfield Context

当前已有实现：

- `libraryPersistence.ts`
  - 已持久化部分阅读状态
- `reader/+page.svelte`
  - 已有阅读状态和位置持久化逻辑
- `library/+page.svelte`
  - 已消费 `lastOpenedAt`、`progressFraction`、`status`

当前问题：

1. reader 里的最新阅读状态何时、如何回流到 library 还不够透明
2. 书库排序和 continue reading 与 reader 持久化之间还没有稳定契约
3. 某些状态字段仍像“能显示出来”，而不是“明确驱动书库行为”

## Scope

In scope:

- 明确 reader -> library 的阅读状态回流契约
- 收口 `lastOpenedAt / progressFraction / status` 如何驱动书架排序
- 必要时补打开/关闭/回库路径上的刷新规则

Out of scope:

- 更高精度的恢复位置算法
- 笔记、书签、搜索缓存
- 在线同步和云端状态

## Deliverables

1. 稳定的 reader -> library 状态回流契约
2. 书架排序与 continue reading 可以依赖这些状态而不是猜测
3. 回库、重开和重新排序行为更接近 `Readest`

## Execution Plan

### Wave 1: 审计回流链路

1. 追踪 reader 侧现在写回了哪些字段
2. 明确 library 当前消费了哪些字段
3. 找出仍然依赖偶然刷新或隐式 reload 的位置

### Wave 2: 固化排序输入

1. 定义哪些字段直接决定 continue reading 和书架排序
2. 移除“展示上看起来对，但输入层不稳定”的路径
3. 必要时让回库时刷新更显式

### Wave 3: 验证回流闭环

1. 打开一本书，返回书库，确认状态更新
2. 再次打开并排序，确认 continue reading 和书架顺序一致
3. 补 focused 回归或 smoke

## Verification Checklist

- `pnpm check`
- `pnpm exec playwright test tests/e2e/library-smoke.spec.ts`
- 如需要：`pnpm exec wdio run wdio.conf.ts --mochaOpts.grep ...`
- `git diff --check`

## Done When

1. 阅读状态变化能稳定反映到书库
2. continue reading / 最近阅读不再依赖手动刷新或偶然重载
3. 排序和 section 规则有明确输入来源

## Not Planned Here

- 不处理 reader 视觉对齐
- 不处理云同步
- 不处理更复杂的跨窗口同步系统
